Findings and open decisions

  • The oracle works and generalises. On held-out dev seeds 50-99, D is 1.00 / 0.98 / 0.99 (easy / medium / hard), at under 0.7 s per episode and never above 28 spend. Over 600 dev episodes it reached the 300-call simulate cap 8 times (2 medium, 6 hard), always ending with a submission. It uses only simulate as its model and stdlib maths; an independent code audit found nothing it knows that an agent does not.
    • Two changes did most of the work: fitting only once every sensor has been read twice (early fits let biases on once-read sensors swallow real faults), and a final one-for-two search (a leak standing in for a neighbouring leak plus a fouled pipe).
    • Rejected during tuning, measured: confirming each bias immediately, refusing biases on once-read sensors, coverage bonuses. Details in docs/oracle_spec.md.
  • F17 fails on 10 of 600 dev seeds: the oracle scores below 0.5. All are mislocated faults (a leak at the neighbouring junction, a missed fouled pipe) or runs that reached the spend or simulate cap; one medium seed scores 0. A normaliser near 0 would hand any agent a score of 1, so finalize normalises only when R_oracle >= 0.5 and reports raw R otherwise. Decision needed: drop such seeds from the shipped set (an extra acceptance rule), or keep them unnormalised.
  • Tool diversity (F19) fails on easy and medium, as measured. speed_step, pump_off_static and reads are used in every episode; valve_step and isolate_branch only when a fault near a valve or inside a branch is in doubt: easy 17% / 0%, medium 3% / 7%, hard 10% / 10%. A speed step returns every flow meter and the static test every pressure and flow sensor, so local probes rarely win on information per unit. Reported as measured rather than engineered around; a Step 6 dial if wanted (e.g. fewer flow meters).
  • Information efficiency fails on easy only (87% vs 90%). The oracle spends about 22 units reading every sensor twice so a stuck sensor cannot hide; on easy there are no sensor faults, so that coverage adds nothing to the true support. It does not infer fault counts from the tier, by design.
  • Gap to the lazy heuristic: fails on easy (impossible), passes on medium (0.35) and hard (0.42). As predicted in Step 4: the lazy heuristic's 0.82 raw on easy leaves no room under 1.
  • The task is too easy (F18), now measured normalised. The lazy heuristic scores 0.88 / 0.59 / 0.47, against the plan's 0.25-0.35 band. Every evidence-free baseline stays under its ceiling (random guess at most 0.041, prior guess at most 0.074, the rest 0). Calibration is Step 6, with this oracle as the instrument.
  • Reward is now normalised in Harbor (F20). Through Harbor on medium:0, the oracle's raw reward 0.87 equals the cache and the reported reward is 1.0. The cache (dev seeds 0-199, all tiers) is generated in the Linux image and matches a macOS run on all 600 entries. Test seeds (1000+) are not cached yet; they come with the shipped task set.
  • Environment risk flagged by the audit. network_mode = "public": if the generator source is ever published, an agent could regenerate plants for the test seeds and read off the faults. The repository is private; this belongs with the open egress decision from Step 3.
  • Still open from earlier steps: judged-run infrastructure and model key (G0); fault-count disclosure; stuck-sensor, eligibility and cap defaults; repair gating; partial-repair weighting (F16); the FP definition.
